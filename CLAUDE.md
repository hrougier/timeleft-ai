# timeleft-ai

One repo, three Claude Code plugins — one per team plus a shared one, the two team plugins chained by a PRD-status handshake:

- **`.claude/skills/product/`** — the product team's workflow over Notion PRDs (build this first)
- **`.claude/skills/shared/`** — plugin-agnostic skills both rosters share (`research`, `grilling`, `glossary-and-decisions`), plus its own `update` (its pin is one of the three CI compares, so it needs a maintainer like the others; no `setup` — it binds nothing). Admission rule: **a shared skill owns a method and never a destination** — bindings are reached by naming a config skill, and a shared skill cannot know whether the session is product's or tech's. The moment a skill needs to say where its output goes, it belongs to the workflow that owns that destination. Chartered 2026-08-09; see its `changelog.md`
- **`.claude/skills/tech/`** — tos v2, chartered 2026-08-08 and **living on the `tech-plugin` branch** until its first slice ships: `main` carries no tech plugin and the catalog does not offer one, because an installable plugin with no skills is worse than none. Its `plugin.json`, `lock.md` and `changelog.md` are on that branch; the design below stays here as the record. The v2 spec is its design, re-based on the four structural findings the product build produced — bindings inside a `config` skill, two hooks not four, one canonical confirmation line, entry-rides-the-commit + version bump

Plugins live under `.claude/skills/` because **placement is the registration** — the CLI's skills-dir auto-discovery is the only local load path, and the root `marketplace.json` is the catalog everywhere else — read today by `/plugin marketplace add hrougier/timeleft-ai`, and later by the org bundle. See `docs/plugin-loading.md` (field-tested rules; do NOT re-attempt settings.json registration) and `docs/github-access.md` (how each audience's code-read credential is scoped, and why the tech plugin's write credential must stay separate).

## Standing doctrines

- **Notion owns nouns, git owns verbs.** All shared state lives in Notion (PRDs, tickets, statuses, contract, glossary). This repo holds only behavior: skills, plugin manifests, internal plumbing. No root CONTEXT.md — cross-team semantics live in Notion. A plugin-internal CONTEXT.md is allowed only for state-machine plumbing vocabulary.
- **Word-for-word vendoring** (tos v2 doctrine — this is the load-bearing rule, do not soften it):
  - For every roster skill, FIRST check upstream `mattpocock/skills` for a counterpart (`skills/engineering/` and `skills/productivity/` — e.g. triage→`engineering/triage`, refine→`engineering/wayfinder`, grilling→`productivity/grilling`, research/prototype/domain-modeling→engineering). If one exists, its text is taken **verbatim** — fetched from the pinned commit, diffed to prove it — and every adaptation is a **patch-only amendment in MP's voice**, individually auditable, recorded as a drift record in `lock.md`. Never write an original skill where a counterpart exists; never compress or restructure MP's text.
  - Only a skill with NO upstream counterpart (product's `draft-prd`, `send-prd-to-dev`, `ask-prd-ai`, `address-prd-feedback`) may be net-new — written as if MP wrote it, matching his structure and length budgets (wrappers ~10 lines, process skills ≤ ~140, heavy material in sibling reference files).
  - Skill prose speaks **abstract tracker verbs** (create a PRD, flip a status, comment). Concrete tool names, property shapes, database IDs, and API mechanics live ONLY in the tracker doc — the file is named **`issue-tracker.md`** (the tos v2 convention name, even though the tracker is Notion; do not invent names like notion-bindings.md). Binding docs ship **inside the config skill** (product's is `skills/product-config/`), and other skills reach them by **naming that skill**, never by a relative path across directories. Field-tested rule: a skill directory and its siblings are the only unit that reaches every surface — other plugin directories may not travel, and the directory depth a relative path is written against is not preserved (claude.ai flattens `<plugin>/skills/ask-prd-ai/` to `product:ask-prd-ai/`). A second binding doc, **`code-repository.md`**, binds "explore the codebase"/"primary sources" to read-only code access (multi-repo, reading delegated to throwaway agents, findings in product language only — never file/function/framework names).
  - Provenance in each plugin's `lock.md` (ONE upstream pin for the whole vendored set + one row per skill: verbatim/adapted + drift record: what changed, why, link). Update-run decisions go in append-only `changelog.md`. Maintained by the plugin's `update` skill.
- **Primary sources & exemplars — read these before writing any skill** (read-only). The tos v2 exemplars live in `timeleft-dev/timeleft-os` on branch `chore/switch-to-release-based-deployment`, **which is not pushed** — `gh` returns 404 for that ref, so they are reachable only from the local worktree at `/Users/hrougier/.supacode/repos/web-restaurant-management-portal/chore/switch-to-release-based-deployment/` (paths below are relative to its root). ## The phase machine (mirror of the Phases DB; that DB is canonical)

**`Phase` (single-valued; the property is named `Phase`, like prod's)**: Problem → Draft → In Refinement → In Design (the prototype ticket's one-way flip — the ticket is blocked by every research and grilling ticket on the map, so it's always the last thing resolved; resolving it leaves the PRD In Design, it never bounces back to In Refinement; a map with no design question skips In Design entirely) → Ready for development (the handoff — tech's inbox) → In development (the issue is filed by tech's triage-issue at pickup; the flip + the Tech-issue link back-fill ride tech's draft-issue, the same shown write that lands the first pass) → In QA (staging deploy, automated later) → Ready to roll out (QA validated, automated later) → Rolled out (prod deploy, automated later). Off the route: On Hold — the PO's siding, set by hand only (skills propose, human decides, comment names why + resume target); Rejected — terminal, kept forever (triage corpus).

**Reviews (court flags on the PRD, parallel + optional, NOT statuses)**: `Data review` and `Tech review`, each — → Requested → Approved / Changes requested. Product plugin sets Requested only; the data lead (human) and tech plugin set their own verdicts. Both can run at once at any product-side status (typically on a Draft — an objection there costs a re-draft, not a re-refine). The bounce = `Tech review: Changes requested` + anchored comments, status unmoved. Declared new data work ⇒ gate requires `Data review: Approved`. Every content write bumps `Rev`; review requests stamp the rev they were made on. Retired statuses (rows kept for history): Ready for data, Ready for product.

Labels chosen so the prod board keeps On Hold and In Design / **Ready for development** / In development / In QA / Ready to roll out / Rolled out survive takeover as-is (prod's "Ready for data review" maps to the Data review property; "PRD in product review" and "Done" dissolve). Two pre-handoff renames are accepted, not accidental: Backlog→Draft (more explicit) and **In PRD→In Refinement** (PO's call, 2026-08-11 — the phase is refinement, and naming one status after the artifact every status shares says nothing; worth one extra rename at takeover).

## Product plugin roster (order of build)

**Every skill name is globally unique across both plugins** — claude.ai's chat surface shows no `product:` prefix, so ten of the eleven original names (`ask`, `triage`, `draft`, `refine`, `address`, `config`, `research`, `grilling`, `prototype`, `domain-modeling`) would have collided with the tech roster's, and picking wrong is silent: tech's `prototype` writes code, product's makes a design artifact. Acts on a PRD take a `-prd` suffix; the rest take a `product-` qualifier.

`ask-prd-ai` (entry point/router, state-aware — mirrors tos:ask) · `triage-prd` (search prior art/rejections → reject-with-citation or hand to drafting; files Problem PRDs with problem statement only) · `draft-prd` (first-pass solution: Problem → Draft) · `refine-prd` (wayfinder-shaped: charts the map as Tickets rows, flips to In Refinement; second mode = checkpoint/challenge) · `design-prd` (ticket resolver, with the shared plugin's `research` and `grilling`; the vocabulary layer is shared too — `glossary-and-decisions`; every resolution session ends by posting the why on the ticket AND folding the what into the PRD; its ticket is blocked by every research and grilling ticket on the map, so it's always the last one resolved; `design-prd` is state-affecting — In Refinement → In Design, one-way, no bounce back) · `address-prd-feedback` (each comment = mini-ticket: fix or reply why not, never silently resolve) · `send-prd-to-dev` (review-with-a-gate: validates product-side → Ready for development; failures become comments) · `product-config` (the bindings vehicle) · `update` (lock.md/changelog.md maintenance) · `setup-product-ai` (**checks reachability, not addresses** — the charter changed when it was built, 2026-08-12: there are no per-workspace IDs to wire, because the team has one board and the tracker doc names it. The `userConfig` design is dropped with them — it existed to make addresses per-install, and it was never verified on claude.ai anyway. What actually fails is whether *this person's session* can reach the four surfaces: the `shared` plugin — tested against the session's own skill list, never a settings page, since the roster depends on it for `research`, `grilling` and `glossary-and-decisions` — the board, the code, and the design tool. All four present identically as "the PRD isn't there", which is why the router sends this ahead of any diagnosis. It writes nothing, so it never asks for a yes, and it carries the plugin's one deliberate voice exception: it must name connectors and screens, because a click has a name. It also owns what no prompt could ever do — walking the human through the PRD template install, whose self-referential view filters are the clicks no API can make)

**Done 2026-08-09:** the resolvers `research` and `grilling` moved out to the **`shared`** plugin (below) and dropped their `-prd` names, and `glossary-and-decisions` followed — its destinations are the same for both plugins (one company glossary; the Decisions DB is already both rosters' ADR corpus), and once it stopped naming them itself nothing else held it here. It kept its name rather than reverting to upstream's `domain-modeling`, at the PO's call. Product's roster reaches them by their shared-plugin names; `design-prd` stayed, because product's prototype is a design artifact and tech's is throwaway code — two skills sharing one name, not one shared skill.

Ticket budget per PRD: **3 research · 3 grilling · 1 prototype** — fold by theme, never cut; overflow goes to the PRD's Not-yet-specified section.

## Tech plugin roster (order of build)

tos v2's roster, adapted so the two plugins mirror each other. Names follow product's globally-unique rule (2026-08-09): every skill says what object it acts on. **Spine**: `config` (the bindings vehicle — `issue-tracker.md` for GitHub, `prd-tracker.md` for the Notion PRD depot, `deployment.md`, `database.md`) · two hooks (`tech-voice.sh` conduct, `tech-binding.sh` injection+nudge) · `setup` (same shape as product's `setup-product-ai`: **reachability, not addresses** — the shared-plugin check against the session's own skill list, then whether this person can reach the repositories, the Specs database and the deployment targets. Whatever genuinely varies per install — which repositories, which release targets — belongs in a binding doc the way product's addresses do, not in a prompt) · `update`. **Decision half**: `triage-issue` (MP + the unfiled-report entry, **and tech's entry point for the handshake** — a `Ready for development` PRD arrives like any unfiled report: verify → file the GitHub issue `needs-triage`, or bounce it, `Tech review: Changes requested` + anchored comments) · `draft-issue` (net-new — first pass *and* the sizing call; for PRD-born work the same shown write closes the handshake: back-fills the PRD's `Tech issue` link and flips `In development`) · `refine-issue` (wayfinder v4: chart / work-through / checkpoint) · `write-issue-spec` (publishes the spec to Notion) · `plan-issue-implementation` (MP's to-tickets; emits the implement chain, blocking order = stack order). **Delivery half**: `implement-issue` (v4 candidate; claim → branch weld → born-draft PR → confidence rule → impl doc) · `address-pr-review` (review round + the history organ) · `rebase` (net-new; restack + pickup, model-invoked) · `merge-pr` (the four checks) · `announce-release`. There is no separate handshake skill — `to-issue` was dissolved into triage-issue (inbox + bounce) and draft-issue (link + flip). **Model-invoked, verbatim, zero patches**: `tdd · code-review · diagnosing-bugs · resolving-merge-conflicts · prototype · grill-with-docs` — **not** `research`, `grilling` or `domain-modeling`, which the shared plugin ships for both rosters (the last as `glossary-and-decisions`). `ask-tech-ai` last — it routes to everything.

Deliberate divergences from the v2 spec (both PO-directed, both recorded in the tech changelog):

- **An issue is not born a map.** triage files a `needs-triage` issue holding the problem; `draft` writes the first pass and sizes it — one slice goes straight to implementation on a yes, an effort goes to `refine`. Same lifecycle as product's triage → draft → refine. Depth stays exactly one (promote, never nest); no PR without a sub-issue.
- **The technical spec lives in Notion**, in the Specs DB related to its PRD — not a committed `.mdx` behind a PR. MP's to-spec already publishes "to the project issue tracker" and asks nothing, so this is a binding change, not a rewrite. Impl docs stay in git, per-slice, on the PR.

Dogfood rig: a **personal GitHub sandbox repo** (real issues, sub-issues, labels, stacked PRs) — the mirror of product's Notion sandbox, not v2's `.scratch/` mock. The v2 spec's `.scratch/` tracker is a *reference for the semantics it reproduced*, never a target to write to.
